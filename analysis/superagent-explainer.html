DSH Superagent 拆解圖鑑

用更多 token，換回人的注意力。

DeepSeek Harness（DSH）團隊在 2026/10/31 發表〈Super-agent 設計探索：邁向更自主的 Agent 系統〉，並開源這份研究原型。它是一個「只服務一個 GitHub repo 的主動型 coding agent」：在 GitHub（和選用的飛書）上聽訊息，有人有權限地請它做事時，開一張 Ticket、在獨立的 Session 與目錄裡完成，再回到原本的對話裡交付，例如一個 PR。這份圖鑑把它拆成 11 個章節，最後一章是給下一個接手的 LLM 的工作手冊。

1,197個測試全過（59 個 spec、15.0k 行），本次實測
9份編號文件 000–008，需依序閱讀
14 + 6Main Session 工具 + Executor 工具
1個 commit（一次性公開匯入）

資料來源：本 repo 的 README、docs/000–008、src 與 tests；鉅亨號〈剛剛，DeepSeek又來掀桌子…〉(post/275433)、〈詳解Super Agent：會主動幹活，更懂何時閉嘴〉(post/275522)。行數為 wc -l 實測。

01 · 問題

為什麼需要 Super-agent

一般 Agent 以「一個 Session」為單位，Session 之間不共享結論，只有使用者自己掌握全貌。DSH 觀察到一個人通常只能同時盯 3 到 5 個活躍 Session。單一任務的上限取決於模型，多任務的上限取決於人的注意力。Super-agent 讓系統接手 Session 管理和上下文同步，人只負責決策和驗收。

連續

在 IM、GitHub 等既有介面互動，感覺只有一個 Agent。IM 裡說方案 A，PR 留言改成方案 B，它接得上。

高效

回應快，多個複雜任務並行，不必等上一個做完。

主動

持續觀察環境事件，值得處理的就推進；不需要介入時保持安靜。

持久

始終在線、接上真實工作環境，長時間運行遇到異常能自動恢復。

02 · 原則 · docs/000-philosophy.md

注意力是唯一的預算

整個專案只有一條核心原則：「Take as little human attention as possible, and give as much value as possible.」每則訊息、通知、問題、設定、面板元素、甚至每段文件都是在花別人的注意力；給不出更多價值的就刪掉。

Agent 什麼時候開口

  • 確認一次請求，說清楚要做什麼（acknowledgement，≤100 字）
  • 有結果可以驗收或使用（result）
  • 需要人做一個決定（一次只問一個具體問題，走結構化的 human_action）
  • 做不完（blocked / failed，誠實回報）

Agent 什麼時候閉嘴

  • 工作中途的進度（progress 只留在 Ticket 內部）
  • 沒有人請、也沒有書面規則允許的事
  • 意圖不明的閒聊：安靜忽略，不追問確認
  • 修好的 review comment 直接 resolve，不寫「已修正」
設計面的推論：概念少、設定少。業務需求要嘛是既有概念的屬性，要嘛是一段 prompt；團隊用文字描述的行為是 prompt 文字，不是設定項。面板只顯示「需要人」的東西，健康狀態不佔空間。
03 · 鳥瞰

全局架構：Router 不做事，Worker 不路由

文章裡的 Router–Worker，在程式碼裡叫 Main Session（orchestrator）與 Executor Session（worker）。兩者都是 DSH 的 Session，差別在 prompt、工具組和 preset。中間夾著一個純同步、無 I/O 的 Engine，它是 Trigger、Thread、Decision、Ticket、Assignment 唯一的寫入者。

和傳統「主 Agent 帶子 Agent」最大的差別：Router 不規劃、不高頻協調子任務。Worker 彼此上下文隔離，靠訂閱同一個 Thread感知彼此；Router 頂多送一則 ≤100 字的 note。

      簡化：未模擬 bot list 比對與「Source 沒在聽這個 scope」的情況。原始碼見 src/policy.ts 的 machineGate 與 gate。

      三種 accept mode

      • off 所有 inferred 都不成為候選
      • observe 預設。inferred 會被評估，正面結果只記成 ignore「would accept」，不接單
      • auto 正面評估且至少命中一條啟用中的 rule，就接單

      explicit 請求在任何 mode 都有效。官方建議：先 observe，看過記錄的 Decision 覺得對了，再切 auto。這就是文章說的「新員工逐步放權」。

      Assessment 必須交出的三個事實

      • 討論對象是這個專案
      • 參與者表達了要實作某個具體變更的意圖
      • 方向已經定案，夠做一個小的局部修改

      每條啟用中的 rule 都要明確判一次 matched true/false，並附上原文引用（intent_evidence）。只有語氣、關鍵字不算數；「也許我們也該像他們那樣顯示未讀數」是偏好，不是請求。見 prompts/admission.md。

      06 · 領域模型 · docs/001-domain.md

      12 個概念，一個都不能多

      程式碼、工具、面板、文件全部只用這組詞彙。上方有色條的是核心領域（Source、Thread、Eval、Mandate、Subscription），其餘是支撐概念。「人」不是領域概念：只是 Trigger 上的 actor 欄位。

      被刻意拒絕的設計（接手時不要加回來）

      被拒絕理由
      Principal / 跨 Source 身分對應人只是 Trigger metadata；同一人在飛書和 GitHub 的對應寫在 prompt（例如 identities skill）
      Eval 自己排程延遲 Trigger需要「等」的條件做成一個 Source，Eval 永遠不等待
      每個 Thread 最多一張 live Ticket一個 Thread 可承載多件獨立工作；重複由 assessment 看 Ticket 清單避免
      「附加到 Ticket」這種 Decision附加就是 Subscription fan-out，不需要 Eval
      Ticket 狀態跟著 DSH Session 走Ticket 可能被交接、恢復、由多個 Executor 執行，所以自己定義狀態
      Policy 變更時取消執行中的 Ticket取消會留下半成品；改為記錄並把變更送進 Ticket
      Executor 宣稱「人叫我停」只有 Eval 能決定 stop 的強度
      從回報自由文字推斷「在等人」需要結構化欄位，Executor 透過 human_action 問
      07 · 執行 · docs/003 · src/core/stage.ts

      Ticket 生命週期：由上往下，第一個符合的列勝出

      每張 open 的 Ticket 只有一個 stage，由「它在等什麼」決定。面板 Overview 就是依這張表排序：person 的列最先出現。調整左側條件，看 ticketStage() 會命中哪一列。

      Ticket 已結束？
      Input 投遞失敗中？
      有待回答的 Attention？
      最新 Assignment
      最新 Report
      blocked/failed 之後有人留言了？
      Stage條件面板標籤
      ended已有 ended已結束
      person / delivery投遞 Input 失敗（2s 起倍增至 1 分鐘重試）Input undelivered
      person / answer有 AttentionAwaiting answer
      person / review最新 Report 為 readyAwaiting review
      person / blocked·failedReport 為 blocked/failed，且之後沒有人留言Blocked · Failed
      working / queued沒有 Assignment，或為 pendingQueued
      idleReport 為 waiting，或 Assignment 已結束Waiting for a Trigger
      working其餘情況Working

      Ticket 怎麼結束

      • ready 且沒有 PR → completed
      • dropped（重現不了、已被取代）→ 安靜結束
      • 有 PR：自己開的 PR 全部 merged/closed 才結束，結果取最後一個 close
      • 人按 Stop → Mandate 被撤回，之後什麼都收不到

      結束不等於死亡

      結束的 Ticket 保留 Mandate 與 Subscriptions。只要不是人叫停的，任何人在它的 Thread 上留言就會直接 resume（先用目前的 Policy revalidate Mandate），不需要重新 Eval。bot 和 CI 訊息不會喚醒它。Subscription 在結束後持續輪詢兩週。

      09 · 持久 · src/app/effects.ts

      可靠性：先記下來，再去做

      Engine 的每個指令在一個交易內改狀態，並把外部動作 enqueue 成 effect；交易 commit 之後 adapter 才真的去做。所以重啟不會遺失、也不會重複。

      Effect做什麼同時重試
      assessment把候選卡片送進 Main Session，送達後才開始算 Eval deadline42s 倍增至 60s
      launchprepare 指令 → 建 Executor Session → 送 assignment 訊息空閒 slot 數暫時性錯誤 5s 倍增至 300s，三次；其餘直接 fail
      delivery把 Ticket 的待送 Input 依序送進執行中的 Assignment42s 倍增至 60s
      relay / noticeWorker 回報、人的 follow-up 送進 Main Session（保序）12s 倍增至 60s
      reply經 Source 送出 Channel 訊息，同 Ticket 同對話依序15s 倍增至 300s
      重啟執行中的 Assignment 以「host restarted」結束，新 Assignment 帶 recovery note：先檢查目錄、git 歷史和 GitHub，再決定要不要重做任何對外動作，最舊的 Ticket 先處理。
      暫停Pause processing 停止派工、新 Eval、Input 投遞和回覆；Source 照常記錄 Trigger，Eval deadline 往後延。
      併發Worker slot 上限可設（1–16），另保留 1 個額外 slot 給「人的留言」，新工作永遠擋不住人繼續推進既有 Ticket。
      背景Shell 前景指令 5 秒後轉背景 job，讓 Worker 下一步就能收新訊息；回合結束後背景工作最多 30 分鐘。
      不刪目前沒有任何清理：trigger、decision、outbox、settings/prompt 版本會無限增長（docs/007 Persistence 段明載）。
      10 · 對照

      文章說的 vs 這份原型實際有的

      README 明說：公開版不等於內部版，文章中部分設計是未來方向。以下依本 repo 的程式碼與文件逐項核對。

      文章中的設計原型狀態在哪裡
      Router–Worker 雙層架構已實作Main Session + 每 Ticket 一個 Executor Session；src/app/sessions.ts、src/executor/dsh.ts
      事件驅動、Trigger已實作GitHub 通知輪詢、飛書事件；src/sources/
      程序層 Fast Path / 語義層 Slow Path已實作Gate src/policy.ts；Assessment prompts/admission.md
      後續訊息直達 Worker已實作Subscription fan-out；src/core/intake.ts
      主動 / 提前行動部分需團隊寫 rule；預設 observe 只記錄不接單，切 auto 才真的動手
      非同步背景執行部分Worker 背景 job / subagent（30 分鐘上限）已有；文章說「已實作但尚未預設開啟」
      存算分離（雲端大腦 + 本機 daemon）部分狀態在 SQLite、可重啟恢復；但大腦與執行在同一台機器，原型中找不到遠端 daemon
      Watchdog 外部監督者未見全 repo 搜尋不到 watchdog；最接近的是 health board 與面板
      鏈式召回 chained recall、長程記憶未見文章列為開放問題
      多 Agent 協作、安全隱私開放問題docs/007 Open questions：哪些 Trigger 欄位可信、部署隔離
      評論文章的保留意見值得一起記住：雙層、事件驅動、存算分離、Watchdog 都是經典系統工程，不是新理論；百人級團隊下 Router 會不會成為瓶頸、Worker 衝突怎麼協調，都還沒有答案。另外，多 Session 設計會多花 token，這正是「用 token 換注意力」的代價。
      11 · 給下一個 LLM

      Brownfield 接手指南

      這份 repo 對 LLM 很友善：文件是編號的、只往前引用；架構文件的模組表被測試強制與程式碼同步；模型看到的所有文字（工具、prompt、skill）都有 size budget 測試。接手時照下面的順序走，通常一輪就能進入狀況。

      閱讀順序（約 2,000 行文件，先讀文件再讀碼）

      1docs/000-philosophy.md：所有取捨的判準。改任何東西前先問「這花不花人的注意力」。
      2docs/001-domain.md：12 個概念與「被拒絕的概念」表。詞彙表在最後，中英對照。
      3docs/002-authorization.md + src/policy.ts：gate、admission table、Mandate revalidation。
      4docs/003-execution.md + src/core/stage.ts：stage 表、slot、重試、重啟。
      5docs/007-architecture.md：當作程式碼索引用，Engine 方法表、模組表、測試表、SQLite 表。
      6src/core/engine.ts → intake.ts → evals.ts → tickets.ts：照依賴順序讀。
      7需要時再讀：docs/004 prompts、005 panel、006 部署、008 新增 Source 的 cookbook。

      不能破壞的不變式

      • Engine 是領域狀態唯一的寫入者；方法全同步，一個指令一個交易
      • src/core 不做 I/O；外部動作只能 enqueue 成 effect
      • Mandate 只有三種改變：accept 建立、人的 stop 撤回、revalidation 失敗撤銷
      • Subscription 只帶上下文，不帶授權；Correlation 只加 context，不路由
      • 外部文字（留言、引用、repo 檔案）永遠是資料，不能改權限
      • 不跨 Source 對應身分
      • Trigger id、Thread key、Channel 位址會持久化，改格式會斷掉舊資料
      • SCHEMA_VERSION 只增不減；改儲存形狀要寫 migration
